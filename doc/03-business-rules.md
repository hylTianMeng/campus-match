# CampusCrew 业务规则、状态机与权限

版本：1.0｜基线日期：2026-10-13｜适用：单校 MVP

配套文档：[产品定义](01-product.md) · [功能需求与验收](02-requirements.md)

## 1. 规则约定

本文实现 DEC 最终基线及本次补充，覆盖初稿冲突。DEC-048 替代 DEC-015 的七天确认期；DEC-013 取消长期 Team/TeamMember；DEC-047 不保留候补；DEC-056 最终版允许管理员访问任意会话全部消息；DEC-066 后台仅五类。原始记录缺 DEC-032，不能补造编号，见 [全量索引](02-requirements.md#7-dec-全量追踪索引)。

**确认级别**：产品权限、容量、时间锁定及已确认的业务结果必须执行。除 `ended` 和 `end_reason=filled/expired/manual` 外，英文状态/原因编码、事务实现、事件名称均为统一实现建议，最终可在详细设计等价调整。涉及未确认业务结果使用 TD 标记，不能把建议升级为既定产品决定。

## 3. 状态模型与转移

### 3.1 招募生命周期与管理限制分离

建议生命周期 `status ∈ {draft, open, ended}`。删除是资源移除动作，不另造“正常结束原因”。正常正式结束必须统一 `ended`，必须记录 `end_reason ∈ {filled, expired, manual}`；未结束不填写正常结束原因。封禁、独立下架作为可并存的限制原因集合，不使用二者覆盖生命周期。

| 当前 | 触发/前置条件 | 下一状态 | 申请及容量影响 | 展示与历史 |
| --- | --- | --- | --- | --- |
| 无 | 手动存草稿；可不完整 | draft | 无 | 仅作者 |
| draft | 作者认证正常、完整校验、至少一岗、有效截止 | open | 开放有空余岗位 | 发布立即公开，不预审 |
| 无 | 直接填写并发布，满足同上 | open | 同上 | 同上 |
| open | 一岗满员，但其他岗未满 | open | 该岗停止新申请，剩余待审未通过/满员 | 其他开放岗位继续招募 |
| open | 所有岗位满员 | ended/filled | 最后录取联动、全部结果锁定 | 默认列表隐藏，正常公开详情保留 |
| open（含隐藏） | 到达截止时间 | ended/expired | 所有仍 pending → expired | 不解除独立下架；历史保留 |
| open | 作者手动提前结束 | ended/manual | 待审终态 TD-03，建议 expired/manual_end | 结果锁定，默认隐藏 |
| open | 管理员独立下架，未结束未到期 | open + admin_takedown | 新申请/审核暂停，待审保留 | 公开内容隐藏；历史必要信息受控 |
| open + admin_takedown | 管理员恢复，仍未截止未结束 | open，移除此原因 | 无其他限制才可继续申请审核 | 通知双方；封禁原因可仍存在 |
| open | 发布者封禁 | open + owner_banned | 暂停交互，历史保留 | 隐藏 |
| open + owner_banned | 解封且未截止未结束 | open，移除此原因 | 无独立下架才恢复 | 不恢复违规下架 |
| draft | 作者删除 | 资源删除 | 无 | 不公开 |
| 已发布且从未有申请 | 作者删除 | 资源删除 | 不能与首个申请同时留下冲突 | 收藏安全处理 TD-10 |
| 已发布且有任何历史申请 | 作者尝试删除 | 不变，拒绝 | 只能在可结束时手动结束 | 保留历史 |
| ended | 重开/改录取/放弃/恢复为可招募 | 不变，拒绝 | 不得修改结果 | 补人新建独立招募 |

已结束且下架内容的后续治理维护入口尚未明确；不能把“恢复未结束、未到期”权限泛化为重开历史招募。已结束一般文字编辑的可用范围也需 TD-02/10 确认，结果锁定不变。

### 3.2 岗位状态

岗位状态建议为派生值而非独立可随意修改的字段；`accepted_count` 只统计当前 accepted。

| 派生状态 | 条件 | 行为 |
| --- | --- | --- |
| available | 招募 open、未截止、无管理暂停、录取数小于容量 | 可收新申请 |
| full | 录取数等于容量且招募尚有其他未满岗 | 不收新申请，该岗其余申请全部未通过/满员 |
| paused | 招募 open 且 发布者下架或管理员封禁 | 不收新申请、不审核；不删待审 |
| closed | 招募 ended 或已到截止时间 | 禁止新申请和结果修改 |

岗位满员不是整条招募独立的 filled 状态；所有岗满员才令招募 ended/filled。未正式结束时撤销或放弃录取释放名额可使岗位重新 available，但不会复活已未通过的历史申请。结束后不再出现释放名额重开。

### 3.3 申请状态及转移

建议 `pending / accepted / not_passed / withdrawn / expired`。必须保存每次提交与变更历史；业务状态与原因分开，不能因统一状态丢失动作差异。

| 当前 | 动作/条件 | 下一状态 | 原因建议编码 | 名额/通知 |
| --- | --- | --- | --- | --- |
| 无 | 合法提交，留言可空 | pending | submitted | 不占名额；新申请通知建议 |
| pending | 作者通过，合法且有名额 | accepted | approved | 占一个名额；录取结果通知 |
| pending | 作者拒绝 | not_passed | rejected | 不占名额；结果通知 |
| pending | 本人主动撤回 | withdrawn | applicant_withdrawn | 不占名额；可再次申请 |
| pending | 同人在同招募一岗通过 | withdrawn | accepted_other_position | 自动撤回其他岗待审 |
| pending | 此岗被他人录取至满员 | not_passed | capacity_full | 不保留候补；结果通知 |
| pending | 发布者拉黑该用户 | not_passed | blocked | 所有本人招募相关待审拒绝；解黑不恢复 |
| pending | 截止正式结束 | expired | deadline_reached | 通知申请者 |
| pending | 作者手动结束 | TD-03：建议 expired | manual_end（建议） | 终态与通知待设计，不冒充 DEC-016 |
| accepted | 作者撤销；未正式结束且允许交互 | not_passed | offer_revoked | 释放名额、保留通过历史 |
| accepted | 本人放弃；未正式结束且允许交互 | withdrawn（建议） | offer_abandoned | 释放名额、通知发布者 |
| accepted | 正式结束 | accepted，锁定 | 保留原原因 | 不再撤销/放弃 |
| not_passed/withdrawn | 被拒绝或自行撤回后合法再申请 | 原记录不变，新增 pending | submitted | 重新检查全部条件 |
| 任意 | 下架/封禁暂停 | 原状态不变 | 限制另存 | 到期仍处理 pending |
| 任意 | 注销关联账号 | TD-05 | 待设计 | 不擅自删除或决定终态 |

DEC-007 明确的是被拒绝和主动撤回后可以再申请，不据此断言过期、自动撤回、撤销录取、放弃等所有情况都有同样入口。可申请资格及记录策略需要 TD-11 保持一致。

## 4. 自动触发优先级与事务并发

已确认的是容量上限、同招募最多一人一岗、截止即结束、满员立即结束、暂停及结果锁定。下述优先级与锁方案是满足这些不变量的**实现建议**，不是新增 DEC，也不预设某种数据库。

### 4.1 请求处理顺序

| 顺序 | 校验或动作 | 目的 |
| --- | --- | --- |
| 1 | 认证会话和基础授权，确定是否可访问该资源 | 不泄露隐藏资源；不允许无权写入 |
| 2 | 锁定/等价串行化招募、相关申请与容量；读取统一服务端时间 | 防止旧页面/旧容量竞态 |
| 3 | 如果生命周期已 ended，拒绝结果修改；否则若当前时刻达到截止，执行 expired 结束 | 截止优先于此时新申请或录取；调度延迟不放行 |
| 4 | 校验当前账号封禁、独立下架、黑名单等限制 | 暂停不允许绕过；旧请求不能沿用旧资格 |
| 5 | 检查申请当前状态、同岗待审唯一性、同人同招募占位唯一性和名额 | 防重复与超额 |
| 6 | 执行业务变更及所有自动联动，保存状态历史 | 不产生对外可见中间状态 |
| 7 | 同事务写入待投递通知事件/等价可靠记录；提交后投递 | 失败不通知成功，支持重试 |

黑名单、封禁、删除、手动结束等竞争操作也必须共享等价的串行化边界。若一个合法操作已在截止前完成提交，后来的截止处理保留它；不得回滚既成通过来伪造时序。服务端精度、提交点及截止判定时点由 TD-02/04 明确。

### 4.2 最后名额录取事务

1. 读取最新招募状态、限制、截止和岗位容量；校验发布者、申请状态及申请者相关资格。
2. 保证该用户在该招募没有另一个 accepted；保证录取数小于名额。
3. 把当前申请变为 accepted 并占一个名额。
4. **先**撤回同一用户在本招募其他岗位的 pending，原因 accepted_other_position；再处理该岗剩余 pending 的满员未通过。这样不把同用户已由另一岗通过而撤回的申请再改写成满员拒绝。
5. 若该岗满员，将剩余 pending 全部 not_passed/capacity_full，不设置候补。
6. 若所有岗位满员，在同一次事务设置招募 ended/filled，锁定全部结果；记录状态历史与事件。
7. 提交。并发请求必须重新读当前结果，不能超额，也不能将已自动处理的申请再次通过。

容量可由原子条件更新、行锁或其他等价一致性机制实现；推荐同用户/招募 accepted 唯一约束和同用户/岗位 pending 唯一约束或等价事务保证。具体锁顺序、死锁重试和存储方案待 TD-04。

### 4.3 其他并发规则

| 竞争 | 必须保持的结果 | 设计建议 |
| --- | --- | --- |
| 两请求申请同一岗位 | 最多一个同时待审 | 唯一约束/原子检查及明确重复反馈 |
| 不同岗位同时录取同一人 | 同招募最多一个 accepted | 招募+用户共享约束；失败方不覆盖成功方 |
| 最后录取与撤销/放弃 | 若满员已结束则后续调整拒绝 | 共用招募串行化；以已提交顺序判定 |
| 拉黑与申请/审核/私信 | 拉黑生效后阻止该方向新交互、待审自动拒绝 | 黑名单与相关业务操作一致性校验 |
| 首个申请与删除 | 无孤立申请；有历史时不能删 | 同一资源锁或等价原子条件 |
| 到期与下架/恢复/解封 | 到期仍 ended/expired，不能恢复成 open | 每次操作先检查截止 |
| 封禁与独立下架 | 两原因可并存、单一恢复不清另一原因 | 原因集合/独立标记 |
| 事件投递重试 | 业务结果一次生效、通知不重复堆积 | 事件 ID+接收者幂等键（建议） |

## 5. 超时与治理影响

| 事件 | 招募 | 申请 | 消息/可见性 | 恢复规则 |
| --- | --- | --- | --- | --- |
| 岗位满员 | 该岗停止申请；全岗满员 ended/filled | 其余待审未通过/满员 | 结果通知 | 未结束释放名额可再申请；旧未通过不恢复 |
| 到期 | ended/expired，即使被隐藏也结束 | 待审 expired，已通过保留并锁定 | 过期通知；正常结束详情保留 | 不重开 |
| 手动结束 | ended/manual | 待审终态 TD-03，已通过锁定 | 对应通知细节待设计 | 不重开 |
| 独立下架 | open+下架，隐藏，不改变截止 | 保留待审，暂停新申请/审核 | 通知发布者及全部曾申请者，申请者无具体原因 | 未结束未截止可人工恢复；仍封禁则不可交互 |
| 发布者封禁 | 全部未结束本人招募隐藏、交互暂停 | 不删存量；到期待审照常过期 | 封禁者登录只读，历史保留 | 解封自动恢复仅因封禁隐藏、未结束未到期者 |
| 申请者封禁 | 不因此改变他人招募生命周期 | 不擅自撤销已通过；其存量是否可被审核 TD-07 | 本人不可申请/发消息/业务写入 | 解封不重写旧申请结果 |
| 拉黑 | 不改变招募生命周期 | 目标对本人全部待审未通过；既有通过不自动撤销 | 禁止被拉黑者发给拉黑者；旧消息/历史保留 | 解黑不恢复原申请 |
| 主动撤回 | 不变 | pending→withdrawn | 保存历史；通知建议 | 有效资格下可重新提交 |
| 拒绝 | 不变 | pending→not_passed/rejected | 原因历史保留 | 有效资格下可重新提交 |
| 撤销录取 | 仅结束前允许；释放岗位名额 | accepted→not_passed/offer_revoked | 区分拒绝原因及历史 | 不自动复活此前满员未通过者 |
| 放弃录取 | 仅结束前允许；释放岗位名额 | accepted→withdrawn（建议） | 通知发布者 | 不重开 ended |
| 注销 | 活动招募处理 TD-05 | 各状态处理 TD-05 | 账号不可继续使用；清理/匿名化不需要的个人信息 | 不擅自规定原邮箱可重注册或历史全部删除 |

独立下架和封禁暂停的已确认限制包括暂停申请/审核或交互。本人撤回、放弃、内容修改等边界未完全明确，列 TD-07；可建议暂停期间全部结果写入禁止，但须作为设计取舍记录，不能冒充已经逐项确认。

## 6. 可见性与隐私

### 6.1 招募、主页及历史

- 访客可公开检索招募，只能看到发布者昵称和头像；完整主页只对校园认证用户开放。
- 已认证用户默认可被搜索，可以关闭；搜索关闭不是招募隐藏、账号封禁或业务退出，也不撤销业务双方必要访问权限。
- 主页“我的发布”默认公开；“我的申请”“我的队伍”默认不公开，可分别开启。公开申请只显示招募与岗位；公开队伍只显示通过招募与岗位，不显示其他成员。
- 关闭“我的发布”控制主页栏目，不能当成把公开招募撤出发现页的开关。隐藏申请栏目也不妨碍发布者查看其招募必要申请信息。
- 正常已结束招募默认列表隐藏，但公开详情及历史入口保留；下架、封禁等管理限制不能通过旧链接或收藏绕过。个人中心可保留必要状态占位，不因此对公众返回受限正文。
- 邮箱、认证凭据、私信、申请留言、举报者身份及管理证据不属于公共搜索内容。账号认证不是允许读取全部历史资料的理由。
- “我的队伍”不生成长期队伍实体。当前 accepted 与“曾通过但后来撤销/放弃”的展示口径须 TD-06 明确；公开栏目不能显示从未通过的申请。

### 6.2 黑名单方向

若 A 拉黑 B，则 B 不得申请 A 发布的任何招募，也不得向 A 发私信；B 对 A 的所有 pending 自动未通过。无需招募关系即可拉黑。历史申请与消息不删除；accepted 不自动撤销；解除不自动恢复。

决策没有确认“双方全面不可见”或“A 同时不能联系 B”，不把初稿黑名单解释扩大为全站双向隐藏。双向都存在黑名单时两个方向各自执行规则。

### 6.3 私信删除、读取与管理透明性

个人消息删除和会话隐藏只改变当前用户视图，不等于双方撤回或服务器彻底销毁；必要记录用于历史与治理。发送者不能查看对方是否已读，内部读取状态仅用于本人未读统计。

管理员可查任意会话全部消息，不限举报上下文，但必须先填访问原因、写入审计，不得修改或伪造正文。产品界面必须明确告知用户该机制；不能把“私信”表述成管理员无法访问。审计保存期限和必要消息保留期限待设计，不作无限保存或法定期限的虚假承诺。

## 7. 举报、处置与管理行为

举报目标为招募、用户、具体私信消息。仅提交举报不改变目标状态，管理员人工核实后决定驳回或采取独立下架/封禁等操作。封禁手动，原因必填，无自动解封期限。

建议举报处理状态 `pending / resolved / dismissed`，是否需要 processing 中间态由 TD-10 选择；业务处置结论与具体处罚动作分别保存，避免下架执行失败却显示“处罚完成”。管理员查私信仍必须先通过访问审计，不因举报工单跳过。

处置完成后通知举报者；采取处罚时通知受处罚者。通知不能暴露举报者身份及可识别身份的证据。下架时发布者可收到处置原因，所有曾申请者只收到安全摘要；多次申请同一招募按接收者去重。管理员可以查看核实所必需的信息，普通用户不能读取他人的完整举报证据。

管理后台只包括用户、招募、举报、分类标签、私信。审计入口嵌入相关管理功能，不以此新增独立统计看板、运营分析、代审批、代注销或重置认证等未经确认能力。

## 9. 审计与历史记录

### 9.1 必需记录

| 记录 | 内容 | 访问与修改边界 |
| --- | --- | --- |
| 私信访问审计 | 管理员身份、会话、访问时间、访问原因；建议请求/关联工单 ID | 返回正文前留痕；普通管理功能不可修改删除；失败不给正文 |
| 封禁/解封记录 | 操作者、目标、动作、时间、封禁原因、前后状态 | 管理必要范围；原因必填；不覆盖旧操作 |
| 下架/恢复记录 | 操作者、招募、原因、前后限制、时间 | 独立于账号封禁；可追溯恢复是否清除相应限制 |
| 举报处置记录 | 举报目标、核实结论、动作、理由、操作者、时间、关联处罚 | 举报者信息受限，不进入受罚通知 |
| 申请操作历史 | 提交、通过、拒绝、撤回、自动撤回、满员、撤销、放弃、过期的时间、原因、操作者/系统事件 | 拒绝与撤销不能只留同一个最终状态；保留重申请历史 |
| 正式结束记录 | 招募、结束时间、end_reason、触发者/事件 | ended 不重开，结束原因不可随意改写为另一时序 |

状态历史建议采用追加记录，而非覆盖现有记录。管理更正若需要，应另写更正事件和理由，不能直接改删旧事实；具体保留、访问授权及防篡改实现 TD-08。审计不应包含密码、验证码或不必要的私信正文副本。

### 9.2 实现数据对象建议

User/个人资料、Category、Tag及用户/招募标签关联、Recruitment、Position、Application及历史、Favorite、Blacklist、Conversation、Message、个人消息可见性、Notification、Report、管理操作与私信访问审计即可支撑 MVP。可以合表或拆表，名称不是已确认数据库结构。

不建立 Team/TeamMember、Comment、Review、Subscription、统计看板实体来恢复初稿范围。录取成员关系直接由申请记录表达；容量若缓存必须与 accepted 真值保持一致。
