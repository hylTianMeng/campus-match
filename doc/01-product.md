## 2. 产品价值主张

CampusCrew 是面向一所学校的校园组队互助与任务型招募匹配平台。它帮助学生把“需要谁来一起完成什么事”表达成可搜索、带岗位名额和截止时间的招募，通过申请、审核及私信完成匹配。

平台服务全校学生，不扩展到跨校或社会招聘。它管理的是招募与匹配结果，不承诺任务实际完成、合作质量或外部活动安全，也不负责组队后的协作管理。

| 当前痛点 | 产品响应 | 价值边界 |
| --- | --- | --- |
| 群消息容易沉底、难以持续发现 | 公开列表、关键词和多条件检索、收藏 | 不做推荐算法或付费曝光 |
| 熟人圈难以找到合适技能的人 | 校园认证用户搜索、技能兴趣标签 | 搜索可见性可关闭，不保证匹配成功 |
| 招募人数、岗位与进度不清楚 | 多岗位独立名额、申请状态、明确结束原因 | 不建立长期团队管理 |
| 重复联系和申请结果不透明 | 独立申请记录、系统通知、私信 | 无对方已读回执，不保证实时送达 |
| 骚扰、违规内容缺乏处理路径 | 用户级黑名单、举报、管理员人工核实与审计 | 举报不自动处罚，不建立信誉评分 |

## 3. 目标用户与典型场景

核心用户是本校已认证学生，既可发布招募，也可申请他人招募。同一用户可并行管理多个招募、申请多个其他招募，不设置互斥身份。

| 场景 | 发起者需求 | 参与者路径 |
| --- | --- | --- |
| 课程项目 | 为某项课程任务寻找不同能力的伙伴 | 搜索课程关键词，选择岗位，申请并等待审核 |
| 学科竞赛 | 招募编程、写作等岗位，各岗独立名额 | 展示自愿公开的资料，与发布者沟通后申请 |
| 科研或社团任务 | 围绕明确任务寻找参与者 | 按分类、技能标签、地点与截止时间筛选 |
| 体育、娱乐与生活互助 | 为一次活动或短期互助寻找搭子 | 浏览公开招募，认证后申请或私信 |

场景不承诺特定成队时长或转化率。分类正式名称、初始标签及活动时间输入格式列入技术设计，不将初稿示例当成固定字典。

## 4. 系统角色、账号状态与业务关系

| 类型 | 名称 | 含义 |
| --- | --- | --- |
| 访问身份 | 访客 | 未登录访问者，可浏览搜索公开招募；仅见发布者昵称头像 |
| 系统角色 | 普通用户 | 使用个人资料、招募、申请、消息等功能；写入权限受认证与封禁限制 |
| 系统角色 | 管理员 | 在五类后台内管理用户、招募、举报、分类标签、私信；敏感操作留痕 |
| 账号状态 | 未认证 / 已认证 | 是否完成校园邮箱验证码验证；登录本身不能代替认证 |
| 账号状态 | 正常 / 封禁 / 已注销 | 封禁账号可登录只读；已注销账号不能继续使用 |
| 业务关系 | 发布者 | 当前招募的所有者，管理该招募及其申请 |
| 业务关系 | 申请者 | 当前申请的提交者，查看、撤回申请或在允许时放弃录取 |

不新增审核员、教师、社团专用账号等系统角色。管理员是否兼有普通业务权限取决于其校园认证及账号状态；管理权限不能直接当作学生业务资格。具体授权方式见待技术设计确认。

## 5. MVP 范围

P0 为本次必须实现并验收的能力。P1/P2 只是范围外候选，不代表用户已经承诺下一次迭代，详见 [需求范围](02-requirements.md#5-非-mvp-范围)。

| 模块 | P0 交付内容 |
| --- | --- |
| 账号与认证 | 校园邮箱+密码注册登录、邮箱验证码认证、一个邮箱一个账号、自主注销身份验证与二次确认 |
| 个人资料与隐私 | 昵称必填；可选头像、学院、年级、简介、技能兴趣标签；选择或创建标签；主页三项独立公开开关；认证用户搜索及搜索可见性设置 |
| 招募与岗位 | 统一表单、固定一级分类、自由标签、文字招募、多岗位独立名额；手动草稿；受限编辑；条件删除；截止或手动结束 |
| 发现与收藏 | 公开浏览、关键词检索、组合筛选、最新发布/即将截止排序、详情与历史入口、我的收藏 |
| 申请与审核 | 多岗位申请、可选留言、发布者审批、重新申请、录取撤销/主动放弃、自动撤回其他岗位待审、满员和到期联动 |
| 消息中心 | 自由一对一文字私信、简单系统通知、全站未读数、可配置约 10 秒 HTTP 轮询、个人侧消息删除和会话隐藏 |
| 治理 | 招募/用户/具体私信举报，人工处置、用户级黑名单，封禁只读及招募暂停/恢复 |
| 管理后台 | 用户、招募、举报、分类标签、私信五类管理；任意会话访问原因和审计；无独立统计看板 |

### 5.1 明确排除

- 跨校平台、企业招聘、支付及资金托管。
- Team/TeamMember、长期成员管理、队伍讨论区、任务执行与外部交流群管理。
- 七天确认期、候补、已结束招募自动重开、关联长期队伍补招。
- 正式邀请与直接加入；私信发送链接后仍须正常申请和审核。
- 招募图片及附件、复杂分类模板、草稿自动保存。
- 智能推荐、热门榜、热门排序、订阅提醒、置顶加急。
- 公开评论、评价信誉体系、音视频、双方消息撤回、WebSocket、发送者可见的已读回执。
- 独立通知平台、业务邮件/短信推送（认证邮件不在此排除）、独立统计看板。

## 6. 核心用户旅程

1. **访客发现**：进入公开列表 → 搜索/筛选 → 查看文字详情及发布者昵称头像 → 注册认证后获得交互权限。访客访问完整主页时被拒绝。
2. **发布与招人**：认证 → 完善昵称 → 保存不完整草稿或填写完整统一表单 → 发布即公开 → 接收申请 → 查看申请者允许公开的资料 → 逐岗审核 → 所有岗位满员立即结束并锁定结果。
3. **申请与匹配**：找到可申请招募 → 选择岗位、可选留言 → 提交待审申请 → 查看结果通知。可以申请同一招募多个岗位；一岗通过后其他待审自动撤回。拒绝/自行撤回后可再次申请，但仍受时间、容量、状态和黑名单限制。
4. **结束前调整**：招募尚未正式结束时发布者可撤销录取，申请者可主动放弃；释放名额。若最后一次录取已使整条招募结束，随后不能再撤销或放弃，需新建招募补人。
5. **沟通与退出平台**：认证学生可直接私信，无需业务关系；可自愿交换外部联系方式。平台只记录匹配历史。注销须身份确认、二次确认，并按最终数据处理方案清理或匿名化资料。
6. **治理**：用户举报或拉黑 → 举报交管理员核实，拉黑立即阻止指定方向的新申请/私信并拒绝相关待审 → 管理员按事实封禁或下架，生成通知与审计；恢复需分别检查封禁和独立下架原因。

## 7. 成功定义与课程验收

成功首先是可重复验证的业务闭环：合法用户可完成发布、检索、申请、审核、通知；容量与结果在并发和截止边界下保持一致；权限和隐私不能通过直接调用接口绕过；管理员处置可追溯。

课程评审以 [功能验收](02-requirements.md#6-综合验收场景) 和 [业务不变量](03-business-rules.md#10-业务不变量) 为依据，提供页面演示、状态转移用例、并发测试及管理审计证据。无需独立统计看板才能验收。

如以后开展产品评估，可观察有效发布量、申请到录取转化、满员结束比例、匹配耗时和举报处置情况，但统计口径、观测期及目标值均未确认。满员并不等于实际合作成功，不虚构 KPI、用户规模、响应时间或法律合规保证。

## 8. 统一术语

| 术语 | 定义 |
| --- | --- |
| 招募（Recruitment） | 围绕一次任务的公开需求；初稿 Post/需求统一称招募 |
| 岗位（Position） | 招募内独立名称、名额和要求；名额表示可录取申请者数量 |
| 申请（Application） | 用户对一个岗位的一次提交；重新申请产生新历史记录 |
| 录取 / 通过 | 申请当前状态为 accepted，占该岗位名额 |
| 我的队伍 | 由通过申请形成的历史组队视图，不是长期队伍实体 |
| 正式结束 | status=ended；end_reason=filled/expired/manual；结果锁定 |
| 下架 | 独立管理限制，不等于正式结束，也不延长截止时间 |
| 封禁暂停 | 因发布者封禁导致的隐藏与交互暂停，区别于独立违规下架 |
| 待审 / 未通过 / 已撤回 / 已过期 | 申请状态；未通过需用原因区分拒绝、撤销录取、满员、拉黑 |
| 用户级黑名单 | 有方向的用户关系，阻止被拉黑者向拉黑者申请及发送私信 |
| 公开主页 | 仅认证用户可访问，并遵守三个公开开关；不公开邮箱、密码或管理证据 |

状态编码及表结构中除明确确认的 ended/end_reason 外，其余英文名称均为统一实现建议，见 [状态模型](03-business-rules.md#3-状态模型与转移)。

## 9. 待技术设计确认

产品范围已闭合，以下事项不通过再次问答扩展 MVP。实现前由技术设计记录取舍，不能冒充已确认决策；会影响用户结果的方案须明确标注后再纳入验收基线。

| 编号 | 未定事项 | 本文边界 |
| --- | --- | --- |
| TD-01 | 校园域名、邮箱标准化、验证码时效/频率、密码找回、会话与异常登录 | 校园邮箱+密码及邮箱一账号已确认；参数未定 |
| TD-02 | 字段长度、时间精度/时区、分类初始字典、分页、头像格式与存储 | 不虚构固定参数；截止判断以服务端一致时间为建议 |
| TD-03 | 手动结束时待审申请终态及对应通知 | 建议 expired+manual_end 原因，与到期一致；不是已确认 |
| TD-04 | 事务锁、截止调度、事件投递、幂等与通知重试 | 原子容量与结束锁定必须成立；技术方案可选择 |
| TD-05 | 注销对活动招募、各类申请、私信、举报和审计的处理及保留期限；原邮箱再注册 | 不擅自完全决定清理策略；已注销账号不可继续使用 |
| TD-06 | 主页 API 投影、搜索关闭后的直接访问、历史队伍展示口径 | 认证和隐私基线不变；撤销/放弃历史是否出现在队伍视图需细化 |
| TD-07 | 下架/封禁暂停期间撤回或放弃、被封禁申请者的存量申请是否可被审核 | 不擅自取消录取或删除历史；操作边界统一设计 |
| TD-08 | 管理员授权、敏感操作访问控制、审计保存和防篡改方式 | 不新增审核员角色；普通后台不可修改删除访问审计 |
| TD-09 | 隐藏会话收到新消息的再显示、个人删除后的未读统计、轮询游标与参数 | 不影响对方消息；保留必要服务器记录；无已读回执 |
| TD-10 | 重复举报、治理目标失效、标签合并引用、内容编辑与历史证据快照 | 维持人工处置及历史可追溯 |
| TD-11 | 自己申请自己招募、已录取者再次申请等边界的错误反馈 | 建议拒绝自申请及在同招募再次占位；不得破坏一人一名额 |
