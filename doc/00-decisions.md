# CampusCrew — MVP 产品决策记录

**项目：** CampusCrew 校园组队互助平台  
**决策范围：** DEC-001 ～ DEC-066  
**状态：** MVP 范围确认完成  
**用途：** 作为 `01-product.md`、`02-requirements.md`、`03-business-rules.md` 的需求依据。

## 一、账号、认证与用户权限

**DEC-002｜校园身份认证**

使用校园邮箱验证学生身份。未经认证的用户不得发布招募、申请岗位或发送私信。

**DEC-020｜游客访问权限**

游客可以浏览、搜索和筛选公开招募。发布、申请及私信操作必须完成校园认证。

**DEC-021｜自由私信**

任意两名已认证学生均可互相发送私信，不要求存在申请或招募关系。

**DEC-022｜用户搜索**

支持按昵称、技能或兴趣标签搜索已认证学生，可进入其个人主页并发起私信。

**DEC-023｜搜索可见性**

认证用户默认允许被搜索，可以自行关闭。关闭后仍可以正常发布和申请招募，相关业务参与者仍可查看必要的个人信息。

**DEC-033｜个人资料字段**

昵称必填；头像、院系、年级、个人简介、技能及兴趣标签均选填。

**DEC-034｜个人主页隐私设置**

用户可以分别设置是否公开「我的发布」「我的申请」「我的队伍」。我的发布默认公开，后两者默认不公开。隐私开关不影响相关业务参与者的必要访问权限。

**DEC-035｜公开申请记录**

开启公开后，其他用户只能查看申请过的招募与岗位，不展示申请状态、留言及审核结果。

**DEC-036｜公开组队历史**

开启公开后，只展示成功加入的招募及对应岗位，不展示其他被录取成员。

**DEC-037｜游客访问个人主页**

游客只能看到招募发布者的昵称和头像。完整个人主页仅向已认证用户开放，并遵守资料公开设置。

**DEC-062｜校园邮箱注册与登录**

校园邮箱直接作为登录账号。通过邮箱验证码完成注册验证后方可使用完整功能。一个校园邮箱只能对应一个账号。

**DEC-063｜技能和兴趣标签**

用户可以选择已有标签，也能创建新标签。管理员负责维护、合并重复标签和处理不合适的标签。

**DEC-065｜账号注销**

用户可以自主注销账号，注销前必须验证身份并二次确认。注销后不得继续使用原账号；不再必要的个人信息应删除或匿名化，关联业务数据的处理规则需要进一步设计。

## 二、招募需求发布与管理

**DEC-003｜先发布后审核**

用户发布招募后立即公开，不需要管理员事先批准。管理员可以事后下架违规内容。

**DEC-004｜多岗位招募**

每条招募可以包含多个岗位，各岗位独立设置招募名额。

**DEC-012｜满员与补招**

招募满员后不自动重新开放。需要补充人员时，发布独立的新招募需求。

**DEC-018｜已发布招募编辑**

发布后允许修改标题、描述、地点和标签等基本信息；不允许修改岗位名额、删除岗位或改变截止时间。

**DEC-019｜禁止新增岗位**

已发布的招募不能新增岗位。新岗位需求应创建新的招募。

**DEC-029｜固定分类与自由标签**

招募必须选择一个系统预设的一级分类。用户可以自由创建标签，分类和标签由管理员维护。

**DEC-030｜统一发布表单**

所有类型的招募使用统一表单。标题、分类、描述、岗位、截止时间等为基础字段；活动时间、地点及标签等可以选填。

**DEC-031｜岗位字段**

岗位名称、招募人数必填；技能标签、岗位描述选填。每条招募至少包含一个岗位。

**DEC-038｜已结束招募展示**

已结束招募不出现在默认招募列表中，但公开详情页和历史记录入口仍保留，受管理员下架等限制的内容除外。

**DEC-044｜草稿功能**

支持手动保存、继续编辑及删除招募草稿。草稿不公开，保存时可以缺少必填项，正式发布时执行完整校验。不做自动保存。

**DEC-045｜图片和附件**

MVP 中的招募需求只支持文字和标签，不支持上传图片或附件。个人头像不受此限制。

**DEC-046｜招募删除**

尚未收到任何申请的已发布招募可以删除。一旦存在申请历史，就不能删除，只能提前结束。草稿可随时删除。

## 三、申请审核与招募生命周期

**DEC-005｜多岗位申请**

同一个用户可以同时申请同一招募中的多个不同岗位，每个岗位分别记录和审核申请。

**DEC-006｜录取后其他申请处理**

某个岗位的申请通过后，同一用户在该招募下其他待审核申请自动撤回。一个用户在同一招募中最多占据一个岗位名额。

**DEC-007｜重新申请**

被拒绝或主动撤回后，可以再次申请同一岗位，但不能同时存在多条相同岗位的待审核申请，且必须遵守黑名单限制。

**DEC-013｜取消独立队伍管理**

不建立长期维护的 Team/TeamMember 队伍管理系统。通过申请记录保存成功组队的历史，「我的队伍」作为历史组队记录页面保留。

**DEC-014｜发布者撤销录取**

招募正式结束之前，发布者可以撤销已通过的申请，释放对应岗位名额。结束后结果锁定。

**DEC-015｜招募确认期（已被覆盖）**

早期曾决定设置满员后七天确认期。此规则已被 DEC-048 正式取代，不得在最终需求中保留。

**DEC-016｜申请自动过期**

招募因到达截止时间而正式结束时，尚未处理的申请自动转为「已过期」，并通知申请者。

**DEC-017｜拒绝与撤销状态**

发布者拒绝申请和撤销录取统一使用「未通过」状态，但必须分别记录原因及操作历史。

**DEC-043｜申请者放弃录取**

招募正式结束前，申请者可以主动放弃已获得的录取资格，释放名额并通知发布者。结束后不能再修改结果。

**DEC-047｜岗位满员处理**

岗位满员后立即停止接收该岗位的新申请，并自动将该岗位其他待审核申请设为「未通过」，原因为「岗位名额已满」。不保留候补机制。

**DEC-048｜取消七天确认期**

所有岗位满员后，整条招募立即结束，录取结果立即锁定。招募也可以因截止时间到达或发布者主动结束而终止。不再设置七天确认期。

**DEC-049｜统一结束状态**

所有正常结束的招募统一使用 `ended`，通过 `end_reason` 区分 `filled`（满员）、`expired`（到期）、`manual`（手动结束）。管理员下架属于独立管理状态。

## 四、搜索、筛选、收藏与邀请

**DEC-024｜主动邀请方式**

不开发正式邀请系统。发布者可以通过私信发送招募链接，对方仍需提交申请并经过正常审核。

**DEC-039｜默认排序**

发现组队页面默认按发布时间倒序排列。发布时间相同时通过唯一 ID 保证排序稳定。

**DEC-040｜多条件筛选**

支持关键词（标题、描述、标签）、一级分类、标签、是否仍可申请、截止时间范围及活动地点筛选，条件可以组合。

**DEC-041｜排序方式**

支持「最新发布」与「即将截止」两种排序方式，默认最新发布。不做热门排序和智能推荐。

**DEC-042｜招募收藏**

认证用户可以收藏和取消收藏招募。个人中心提供「我的收藏」，已结束招募仍保留在收藏记录中，但不能再次申请。

## 五、消息、私信与黑名单

**DEC-001｜统一消息中心**

MVP 支持文字私信和简单系统通知，两者统一放在消息中心，不开发独立的复杂通知平台。

**DEC-008｜用户级黑名单**

拉黑针对用户整体生效。被拉黑者不能申请拉黑者发布的任何招募，也不能向拉黑者发送私信。

**DEC-009｜拉黑后的申请处理**

拉黑后，自动拒绝被拉黑者对拉黑者所有招募的待审核申请。历史记录保留，解黑后不自动恢复原申请。

**DEC-010｜拉黑与成员移除（后续范围调整）**

早期确定拉黑与队伍成员移除互不关联。但 DEC-013 后取消长期队伍管理，因此 MVP 不再实现正式组队后的成员移除功能。

**DEC-011｜后续沟通边界**

用户通过站内私信自愿交换微信、QQ 等联系方式。组队成功后的实际协作、活动进展与外部交流群不属于 CampusCrew 的管理范围。

**DEC-059｜消息轮询**

采用 HTTP 定时轮询获取新私信和系统通知。建议间隔约 10 秒，具体实现可调整。MVP 不使用 WebSocket。

**DEC-060｜全站未读提醒**

导航栏显示消息入口及未读数量。用户位于其他页面时也会定期更新未读数量。

**DEC-061｜私信已读回执**

内部记录消息是否已读，用于未读统计，但发送者不能查看对方是否已读。

**DEC-064｜私信删除与隐藏**

允许用户仅对自己删除消息或隐藏会话，不影响对方看到的内容。服务器保留必要记录，MVP 不支持双方消息撤回。

## 六、举报、审核与管理员权限

**DEC-025｜举报功能**

支持举报招募需求和用户，并在私信管理规则中扩展到举报具体消息。管理员可以审核举报，采取下架、封禁或驳回等措施。

**DEC-026｜举报后人工处理**

举报不会自动导致封禁或下架。必须经过管理员核实，由管理员决定是否处罚。

**DEC-027｜封禁后招募处理**

用户被封禁后，其所有尚未结束的招募自动隐藏并暂停交互。历史记录保留。

**DEC-028｜解封后恢复招募**

解封时，自动恢复仅因账号封禁而暂停、尚未截止且尚未正式结束的招募。独立违规下架的招募不自动恢复。

**DEC-050｜管理员恢复招募**

管理员可以恢复尚未截止、未正式结束的下架招募。下架不会延长截止时间，并保留原有申请记录。

**DEC-051｜下架期间申请处理**

招募下架期间暂停新申请和审核，保留申请状态。截止前恢复后可以继续审核；截止时间到达后正常结束，待审申请过期。

**DEC-052｜下架通知**

管理员下架招募后，通知发布者及所有曾提交申请的用户。申请者不查看具体下架原因。

**DEC-053｜恢复通知**

管理员恢复招募后，通知发布者和所有曾提交申请的用户。

**DEC-054｜账号封禁与解封**

管理员可以手动封禁和解封用户。封禁必须填写原因，不设置自动解封期限，保留管理操作记录。

**DEC-055｜封禁用户的权限**

被封禁用户可以登录和查看历史内容，但不得发布、申请、审核、发送私信或进行其他业务写入操作。

**DEC-056｜管理员私信权限（最终修订版）**

管理员拥有查看全部用户私信会话的权限，不限于举报消息，但不得修改、伪造消息。平台需要明确告知用户这一管理机制。此前仅允许查看举报上下文的方案已被取代。

**DEC-057｜私信查看审计**

管理员查看私信前必须填写原因。系统记录管理员身份、会话、查看时间和原因。普通管理功能不能修改或删除审计记录。

**DEC-058｜举报处理通知**

举报处理完成后通知举报者；如果采取了处罚措施，同时通知被处罚者。不得向被处罚者泄露举报者身份及可能暴露身份的证据。

**DEC-066｜MVP 管理后台范围**

只实现五类后台功能：用户管理、招募管理、举报管理、分类与标签管理、私信管理。不开发独立的数据统计看板。

## 七、后续决策对旧方案的覆盖

以下内容在整理正式需求时尤其需要注意：

1. **DEC-013 覆盖早期的独立队伍管理设计。** 保留「我的队伍」历史页面，但不维护长期队伍实体。
2. **DEC-048 覆盖 DEC-015。** 不再存在七天确认期，所有岗位满员后立即结束。
3. **DEC-047 确认采用岗位满员后自动拒绝待审核申请。** 不使用候补或满员后补录机制。
4. **DEC-056 使用最终修订版。** 管理员有权查看全部私信，访问时按 DEC-057 留痕。
5. **DEC-017 统一拒绝与撤销的最终状态。** 仍须保存不同原因及必要历史。
6. **DEC-066 排除独立统计看板。** 不应将它作为 MVP 必需功能。

## 八、尚待技术设计细化的事项

当前产品范围已经确认，但以下内容不宜擅自解释为已经做出的产品决策：

- 校园邮箱允许的具体域名、验证码有效期与发送频率限制。
- 登录会话、密码找回、异常登录等账号安全细节。
- 状态转换的事务处理、并发录取名额控制、自动截止任务的执行方式。
- 主动提前结束招募时待审核申请的具体终态与对应通知。
- 用户注销时，对未完成招募、申请、私信及审计数据的清理和匿名化规则。
- 用户身份搜索可见性、主页公开设置的 API 权限实现。
- 管理员权限的授权方式及审计记录保存期限。
- 具体表结构、接口名称、UI 组件、分页数量和技术架构。

这些事项可以在后续详细设计阶段作出实现建议，并明确标记为建议或待确认项。
